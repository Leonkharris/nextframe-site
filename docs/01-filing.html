Why

That sentence is from the meeting, not from me. It is the whole case for this document.

"You go looking for something and it might be in Notion, it might be in Google Drive, it might be in your own files. But when I go looking, sometimes the answer comes out different. That means the data isn't consistent."

And the demonstration, on the same call: a contract was handed to an AI tool to fill in a form, and it returned the wrong figures. The full discussion →

What was agreed
Classify, consolidate, then choose

Do not pick the database first. Get the structure and the material right, then let engineering pick storage and migrate — "DB migration is fast, building a DB is not." Start in Google Drive because everyone can actually use it.

What went wrong last time
A convention existed and lapsed

"Do you remember, early on I made a document on file naming and management paths? You've probably forgotten." It was written partly to prepare for AI search. This one is shorter for that reason.

The rule

If two people could disagree about where it lives, it is in the wrong place

Everything below is just that rule applied. If a case is not covered, apply the rule and tell whoever owns this so the gap gets written down.

📍

One home per thing. A document lives in exactly one folder. If two teams need it, they link to it — they do not keep a copy. A second copy is how the answers start disagreeing.

Structure

A proposed top level

The meeting called for a master folder for the corporation and then per-department folders. The entity names below are taken from what the recordings actually mention — correct them before this goes anywhere, because some are phonetic guesses from a translated transcript.

By function, across brands

10-Clients/One folder per operator or agency. Contracts, rates, meeting records, requests.
11-Providers/One per game provider. Rates, game lists, assets, integration notes.
12-Legal/Licences, jurisdiction answers, the written legal views the meetings keep promising.

14-Brand/Logos, colour, typefaces, the creative kits.

🔢

Why the number prefixes. They keep the order stable and meaningful instead of alphabetical, so the list looks the same to everyone and nothing drifts to the bottom because somebody renamed it. Leave gaps in the numbering so a new folder does not force a renumber.

❓

The one real decision in this section. Brand-first or function-first? A provider rate card belongs to the provider; a provider's game list as deployed on Xsino belongs to Xsino. Both splits are defensible and the wrong answer is to do both at once. The proposal above is function wins for anything contractual, brand wins for anything operational — but that is exactly the kind of call that should come from whoever actually files these every day, not from this page.

Naming

Four rules, and nothing else

Every extra rule is a rule somebody will not follow. These four are the ones that make a file findable by a person and parseable by a tool.

1

Dates are YYYY-MM-DD, always, at the front

2026-09-30-xsino-performance-review.pdf. Sorts correctly, never ambiguous between US and European order, and a tool can read it without guessing.

This single rule would have prevented the mess in the recordings folder, where one meeting carries two different dates in two file names and neither is verifiable.
2

Lower case, hyphens, no spaces

peter-and-sons-rate-card.pdf, not Peter & Sons Rate Card (final) v2.pdf. Spaces and ampersands break scripts, URLs and command lines; a tool that has to quote every path will eventually fail to.

3

Versions are -v2, and "final" is banned

-v2, -v3, at the end, before the extension. No final, FINAL, final-real, final-2. If something is superseded it moves to an _archive/ subfolder in the same place, so the current version is the only one in view.

4

The name says what it is, not who made it or when you got it

trafficjunky-media-kit.pdf, not MediaKit.pdf sitting in a Telegram download folder. The name is the only thing most people and every search tool will ever read.

The hard part

Why the last one lapsed, and what would stop this one

A convention is not a document problem. It is a habit problem, and habits need one owner and one moment of enforcement.

1
One named owner

The meeting has this — somebody committed to driving it personally, one folder at a time. Keep that. A convention owned by "everyone" is owned by nobody.

2
Start with what is already moving

Do not migrate the archive first. Apply it to the next thing produced, then the next. The meeting records already follow it and are a working example to point at.

3
One place to ask

When a case is not covered, somebody has to answer within the day and add a line here. Unanswered edge cases are where conventions die.

4
Do not wait for the database

Picking the storage comes after this. If the structure is right, migration is cheap; if it is wrong, no database saves it.

📉

And keep the scope honest. From the same meeting: a perfect version of this answers roughly 30% of what partners ask. The rest are account-level issues and provider-side faults that are not in our documents at all, and never will be. Knowledge capture was described as "about 20% of the thing" — which is right, and is an argument for doing it properly rather than for not doing it.

🤖

What this unlocks. Every assistant proposed across these meetings — the WhatsApp chatbot, the partner-question bot in Telegram, the internal triage bot — reads from this material. Engineering confirmed the connection itself is solved: "I'm certain it can be done, because I've done it before." The structure is the only blocker, and it is the cheap part.
